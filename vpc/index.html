AWS 위에 내 IP 대역으로 네트워크를 그리세요

Amazon VPC는 AWS 안에서 논리적으로 격리된 가상 네트워크입니다. CIDR 블록을 정하고, 가용 영역마다 서브넷을 나누고, 라우팅 테이블과 게이트웨이로 트래픽이 갈 길을 정합니다. 다른 모든 AWS 네트워킹 서비스가 이 위에서 동작합니다.

Why Amazon VPC

모든 AWS 네트워크의 출발점

EC2, RDS, EKS, Lambda의 VPC 연결까지 사설 네트워크가 필요한 리소스는 모두 VPC 안의 서브넷에 ENI를 둡니다. 주소 체계, 경로, 접근 통제를 처음 한 번 잘 설계하면 이후의 하이브리드 연결과 멀티 VPC 확장이 쉬워집니다.

Isolate

계정 · 리전 단위로 격리된 네트워크

VPC는 한 리전에 속하고 다른 VPC와 기본적으로 분리됩니다. 온프레미스와 겹치지 않는 사설 대역을 직접 정합니다.

Route

라우팅 테이블이 곧 정책

서브넷마다 연결된 라우팅 테이블이 IGW, NAT, 엔드포인트, 피어링, TGW 중 어디로 보낼지 정합니다.

Control

두 겹의 필터

ENI에는 stateful 보안 그룹, 서브넷 경계에는 stateless 네트워크 ACL을 겁니다. 계정 전체는 Block Public Access로 막습니다.

Route tables

서브넷의 성격은 라우팅 테이블이 정합니다

"퍼블릭 서브넷"이라는 설정값은 따로 없습니다. 기본 경로가 인터넷 게이트웨이를 가리키면 퍼블릭, NAT 게이트웨이를 가리키거나 아예 없으면 프라이빗입니다. 아래는 앱 계층 프라이빗 서브넷의 라우팅 테이블 예시입니다.

목적지가 여러 경로에 맞으면 가장 구체적인 프리픽스가 이깁니다. local 경로는 지울 수 없습니다.

local

VPC 안은 항상 통한다

VPC CIDR 전체에 대한 local 경로가 모든 라우팅 테이블에 자동으로 들어갑니다. 서브넷 사이 통신을 막으려면 라우팅이 아니라 보안 그룹이나 NACL을 씁니다.

IGW · NAT

인터넷으로 나가는 두 갈래

IGW는 공인 IP가 있는 리소스의 양방향 통신을, NAT 게이트웨이는 프라이빗 리소스의 아웃바운드 IPv4만 처리합니다. IPv6 아웃바운드 전용은 egress-only IGW입니다.

VPCE · PCX · TGW

사설 경로

게이트웨이 엔드포인트는 prefix list 경로로, 피어링과 Transit Gateway는 CIDR 경로로 붙습니다. 인터페이스 엔드포인트는 경로가 아니라 DNS와 ENI로 연결됩니다.

설계 포인트: 라우팅 테이블은 AZ 단위로 나누는 것이 기본입니다. 각 AZ의 프라이빗 서브넷이 같은 AZ의 NAT 게이트웨이를 가리켜야 한 AZ 장애가 다른 AZ의 인터넷 출구를 끊지 않습니다.

Features

주요 기능

Internet gateway

IGW와 egress-only IGW

IGW는 VPC당 하나씩 붙는 수평 확장형 게이트웨이로, 공인 IPv4에 대해 1:1 NAT를 수행합니다. egress-only IGW는 IPv6 아웃바운드만 허용하고 인바운드 연결 시작은 막습니다.

NAT gateway

관리형 NAT

5 Gbps에서 시작해 100 Gbps까지 자동 확장하고, IPv4 주소를 최대 8개(주소당 목적지별 동시 연결 55,000개) 붙입니다. 퍼블릭 · 프라이빗 유형이 있고 NAT64도 지원합니다. regional 모드는 퍼블릭 서브넷 없이 VPC 단위로 만들고, 워크로드가 있는 AZ로 자동 확장되며 AZ당 IP를 최대 32개까지 씁니다. 프라이빗 NAT는 zonal 모드에서만 됩니다.

VPC peering

VPC 피어링

두 VPC를 사설 IP로 1:1 연결합니다. 계정과 리전을 넘을 수 있지만 전이 라우팅은 안 되고 CIDR이 겹치면 연결할 수 없습니다. 많은 VPC를 엮을 때는 Transit Gateway를 씁니다.

VPC endpoints

게이트웨이 · 인터페이스 엔드포인트

S3와 DynamoDB는 무료 게이트웨이 엔드포인트로, 그 밖의 AWS 서비스와 SaaS는 PrivateLink 기반 인터페이스 엔드포인트로 인터넷을 거치지 않고 접근합니다.

IPAM

VPC IP Address Manager

조직 전체 IP 대역을 풀로 나눠 계정과 리전에 할당하고, 겹침과 사용률을 모니터링합니다. BYOIP, Amazon 제공 연속 IPv6 블록, Public IP Insights를 함께 다룹니다.

Block Public Access

VPC BPA

리전 단위로 IGW · EIGW 경로를 권한 있게 차단합니다. bidirectional 모드는 양방향을, ingress-only 모드는 인바운드만 막고 NAT · EIGW 아웃바운드는 허용합니다. 필요한 VPC나 서브넷만 exclusion으로 뺍니다.

Encryption Controls

VPC Encryption Controls

VPC 안과 VPC 간 트래픽의 전송 중 암호화 상태를 모니터링하고 강제합니다. monitor 모드에서 Flow Logs의 encryption-status로 평문 흐름을 찾고, enforce 모드에서는 암호화를 지원하지 않는 리소스 생성을 막습니다. IGW, NAT 등 정해진 리소스만 exclusion으로 둡니다.

Route Server

VPC Route Server

VPC 안의 방화벽 · 라우터 어플라이언스와 BGP(BFD 선택)로 피어링해, 최적 경로를 서브넷 · IGW 라우팅 테이블에 동적으로 넣습니다. 어플라이언스 장애 시 스크립트 없이 경로가 페일오버됩니다.

VPC sharing

서브넷 공유 · SG 재사용

AWS RAM으로 서브넷을 조직 내 다른 계정과 공유해 한 VPC를 여러 계정이 씁니다. 보안 그룹은 VPC associations로 같은 계정 · 리전의 다른 VPC에 연결하거나 공유 VPC 참여 계정과 공유합니다.

Security groups vs NACLs

보안 그룹과 네트워크 ACL, 어디에 무엇을 쓸까

두 필터는 서로 대체재가 아니라 겹쳐 쓰는 층입니다. 세밀한 허용 정책은 보안 그룹으로, 서브넷 경계의 거친 차단은 네트워크 ACL로 나눕니다.

Reference architecture

2개 AZ, 3계층 VPC

계층마다 AZ별 서브넷을 하나씩 두고, 각 AZ의 앱 서브넷은 같은 AZ의 NAT 게이트웨이로 나갑니다. S3는 게이트웨이 엔드포인트로, 다른 AWS 서비스 API는 인터페이스 엔드포인트로 사설 경로를 탑니다.

Getting started

VPC를 설계하는 순서

  1. STEP 1

    주소 계획

    온프레미스, 다른 VPC와 겹치지 않는 CIDR을 정합니다. 여러 계정 · 리전이면 IPAM 풀에서 할당합니다.

  2. STEP 2

    VPC · 서브넷 생성

    2개 이상 AZ에 계층별 서브넷을 만듭니다. 콘솔의 "VPC and more"로 한 번에 만들 수 있습니다.

  3. STEP 3

    게이트웨이 · 라우팅

    IGW, AZ별 NAT 게이트웨이(또는 regional NAT)를 만들고 서브넷마다 라우팅 테이블을 연결합니다.

  4. STEP 4

    필터 · 엔드포인트

    보안 그룹을 계층별로 나누고, S3 게이트웨이 엔드포인트와 필요한 인터페이스 엔드포인트를 추가합니다.

  5. STEP 5

    가드레일 · 가시성

    Block Public Access로 의도치 않은 인터넷 노출을 막고, Flow Logs와 Reachability Analyzer로 경로를 확인합니다.

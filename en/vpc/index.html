Amazon Virtual Private Cloud · Isolated virtual network

Draw your network on AWS with your own IP ranges

Amazon VPC is a logically isolated virtual network within AWS. You choose CIDR blocks, carve subnets in each Availability Zone, and use route tables and gateways to decide where traffic goes. Every other AWS networking service runs on top of it.

Why Amazon VPC

The starting point for every AWS network

Every resource that needs a private network, from EC2, RDS, and EKS to Lambda VPC connectivity, places an ENI in a subnet inside a VPC. Get the addressing, routing, and access control right once, and later hybrid connectivity and multi-VPC growth become much easier.

Isolate

A network isolated per account and Region

A VPC belongs to one Region and is separated from other VPCs by default. You choose private ranges that don't overlap with on-premises.

Route

The route table is the policy

The route table associated with each subnet decides whether traffic goes to an IGW, NAT, endpoint, peering connection, or TGW.

Control

Two layers of filtering

Apply stateful security groups to ENIs and stateless network ACLs at subnet boundaries. Lock down the whole account with Block Public Access.

Route tables

The route table defines what a subnet is

There is no "public subnet" setting. If the default route points to an internet gateway, the subnet is public; if it points to a NAT gateway or there is none, it is private. Below is an example route table for a private app-tier subnet.

When a destination matches several routes, the most specific prefix wins. The local route can't be deleted.

local

Traffic inside the VPC always flows

A local route for the entire VPC CIDR is added to every route table automatically. To block traffic between subnets, use security groups or NACLs, not routing.

IGW · NAT

Two ways out to the internet

An IGW handles two-way traffic for resources with public IPs; a NAT gateway handles only outbound IPv4 from private resources. For outbound-only IPv6, use an egress-only IGW.

VPCE · PCX · TGW

Private paths

Gateway endpoints attach through prefix list routes; peering and Transit Gateway attach through CIDR routes. Interface endpoints connect through DNS and ENIs, not routes.

Design tip: Split route tables per AZ by default. Each AZ's private subnets should point to the NAT gateway in the same AZ so that one AZ failure doesn't cut internet egress for the others.

Features

Main features

Internet gateway

IGW and egress-only IGW

An IGW is a horizontally scaled gateway, one per VPC, that performs 1:1 NAT for public IPv4 addresses. An egress-only IGW allows only outbound IPv6 and blocks inbound connection initiation.

NAT gateway

Managed NAT

Starts at 5 Gbps and scales automatically to 100 Gbps, with up to 8 IPv4 addresses (55,000 simultaneous connections per destination per address). Comes in public and private types and supports NAT64. Regional mode is created per VPC without a public subnet, expands automatically to AZs where workloads run, and uses up to 32 IPs per AZ. Private NAT is available only in zonal mode.

VPC peering

VPC peering

Connects two VPCs 1:1 over private IPs. It can cross accounts and Regions, but transitive routing isn't supported and overlapping CIDRs can't be connected. To interconnect many VPCs, use Transit Gateway.

VPC endpoints

Gateway and interface endpoints

Reach S3 and DynamoDB through free gateway endpoints, and other AWS services and SaaS through PrivateLink-based interface endpoints, without traversing the internet.

IPAM

VPC IP Address Manager

Divides your organization's IP space into pools, allocates them to accounts and Regions, and monitors overlap and utilization. Also covers BYOIP, Amazon-provided contiguous IPv6 blocks, and Public IP Insights.

Block Public Access

VPC BPA

Authoritatively blocks IGW and EIGW routes per Region. Bidirectional mode blocks both directions; ingress-only mode blocks only inbound and allows NAT and EIGW outbound. Exempt only the VPCs or subnets that need it with exclusions.

Encryption Controls

VPC Encryption Controls

Monitors and enforces encryption in transit for traffic within and between VPCs. In monitor mode, find plaintext flows with the encryption-status field in Flow Logs; in enforce mode, creating resources that don't support encryption is blocked. Only designated resources such as IGWs and NAT can be exclusions.

Route Server

VPC Route Server

Peers over BGP (optionally with BFD) with firewall and router appliances in the VPC and dynamically installs the best routes into subnet and IGW route tables. Routes fail over on appliance failure without scripts.

VPC sharing

Subnet sharing and SG reuse

Share subnets with other accounts in your organization through AWS RAM so several accounts use one VPC. Security groups can be associated with other VPCs in the same account and Region through VPC associations, or shared with participant accounts of a shared VPC.

Security groups vs NACLs

Security groups and network ACLs: what goes where

The two filters aren't substitutes; they're layers you stack. Use security groups for fine-grained allow policies and network ACLs for coarse blocking at subnet boundaries.

Reference architecture

Three-tier VPC across two AZs

Each tier has one subnet per AZ, and each AZ's app subnet egresses through the NAT gateway in the same AZ. S3 traffic uses a gateway endpoint and other AWS service APIs use interface endpoints, so both stay on private paths.

Getting started

Steps to design a VPC

  1. STEP 1

    Plan addressing

    Choose CIDRs that don't overlap with on-premises or other VPCs. For multiple accounts and Regions, allocate from IPAM pools.

  2. STEP 2

    Create the VPC and subnets

    Create tiered subnets in two or more AZs. The console's "VPC and more" option creates them all at once.

  3. STEP 3

    Gateways and routing

    Create an IGW and per-AZ NAT gateways (or a regional NAT gateway), and associate a route table with each subnet.

  4. STEP 4

    Filters and endpoints

    Split security groups by tier, then add an S3 gateway endpoint and the interface endpoints you need.

  5. STEP 5

    Guardrails and visibility

    Prevent unintended internet exposure with Block Public Access, and verify paths with Flow Logs and Reachability Analyzer.

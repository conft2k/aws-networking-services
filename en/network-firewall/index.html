Why Network Firewall

When you need inspection beyond security groups and NACLs

Security groups and network ACLs allow or deny traffic by IP address and port. When you need domain-based outbound control, protocol detection, or signature-based intrusion prevention, add a firewall layer.

Managed

Scaling without the operational burden

Scales automatically with traffic, and AWS manages availability and resiliency. You don't run appliance instances yourself.

Inspect

Deep, flow-level inspection

Identifies protocols such as HTTPS regardless of port, and inspects packet payloads with rules.

Central

One policy, many VPCs

A single firewall policy manages endpoints in multiple VPCs or a Transit Gateway attachment.

Stateful rules

Write rules in native Suricata syntax

Below is an example outbound allowlist. Under strict order, the default for new firewall policies, rule groups are evaluated by priority and rules within a group in the order they are written.

  1. Strict order Default · recommended

    The default for new policies. Rule groups are evaluated from the lowest priority number, and rules within a group in the order you define them. The policy sets the default action for traffic that matches no rule; new policies default to Application drop established (server-directed only).

  2. Action order Legacy

    Kept for compatibility with existing policies. All pass rules are evaluated first, followed by drop, reject, and alert. Within the same action, the priority keyword sets the order. The rule group's evaluation order must match the policy's.

  3. reject is TCP only

    Blocks matching traffic and sends a TCP RST to the sender. It can't be used with the FTP and IMAP protocols.

Features

Key features

Stateless

Stateless rules

Judges each packet without flow context, by source and destination, port, and protocol. The action is pass, drop, or forward to the stateful engine.

Domain filtering

Domain list rules

Identifies the domain from the TLS SNI for HTTPS and the Host header for HTTP. Beyond allow and deny lists, you can use reject and alert actions, and match all subdomains with entries such as .example.com.

TLS inspection

TLS inspection

Uses ACM certificates to decrypt encrypted traffic, hand it to the stateful engine, and re-encrypt it. Inbound uses server certificates; outbound uses an imported CA certificate. With session holding on, connection setup packets aren't sent to the destination until SNI rules are evaluated.

Managed rules

AWS managed rule groups

Add domain and IP, and threat signature (StrictOrder and ActionOrder versions) managed rule groups, plus AWS Marketplace partner rule groups, to a policy. Active threat defense, based on Amazon threat intelligence, is on by default when you create a new policy in the console and is billed separately.

Multi-VPC

Endpoints in multiple VPCs

VPC endpoint associations place one firewall's endpoints in other VPCs. Share the firewall through AWS RAM to protect VPCs in other accounts with the same policy. All endpoints share the per-AZ throughput.

Logging

Alert · Flow · TLS logs

Choose Amazon S3, CloudWatch Logs, or Amazon Data Firehose as the destination for each log type. Matches on drop, alert, and reject rules are written to the alert log.

Web categories

URL and domain category filtering

Write rules using predefined web categories such as GenAI, social media, and streaming. Combined with TLS inspection, you get finer control at the URL level.

Containers

Container attribute-based rules

Target rules by Amazon EKS namespace, cluster, and label, or by Amazon ECS cluster and attributes. Wildcards are supported, at no additional charge.

Preview

Explicit forward proxy

Running explicit proxy mode under the same firewall policy is in public preview (August 2026, US East (Ohio)). It isn't generally available yet, so don't build it into production designs.

Reference architecture

Central inspection attached directly to Transit Gateway

Spoke VPC and on-premises traffic follows the TGW route tables to the firewall attachment. The VPC the firewall uses is managed by Network Firewall and isn't visible to you; traffic that passes inspection continues to the destination VPC or the egress VPC.

Getting started

Steps to deploy your first firewall

  1. STEP 1

    Write rule groups

    Create stateless and stateful rule groups, or choose managed rule groups.

  2. STEP 2

    Firewall policy

    Combine rule groups and set the evaluation order (strict order by default) and default actions.

  3. STEP 3

    Create the firewall

    Specify the VPC and a firewall subnet per AZ, or attach directly to a Transit Gateway (shared through RAM if another account owns it).

  4. STEP 4

    Update routing

    In the VPC or TGW route tables, set the firewall endpoint or attachment as the next hop.

  5. STEP 5

    Logging and validation

    Turn on alert and flow logs, and confirm that allows and blocks behave as intended.

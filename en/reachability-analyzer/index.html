VPC Reachability Analyzer · Static configuration analysis · Connectivity troubleshooting

Find where the path breaks without sending a packet

Reachability Analyzer builds a model of the network configuration between a source and a destination and determines whether the destination is reachable. It sends no traffic. If the destination is reachable, it shows the hop-by-hop path; if not, it shows the blocking component and the reason.

Why Reachability Analyzer

Answer "why can't it connect?" with configuration evidence

Connectivity problems arise where route tables, security groups, network ACLs, load balancers, and TGW routing overlap. Instead of opening console pages one by one, define a single path and run an analysis.

Static

Diagnosis without sending packets

Because the verdict comes from configuration alone, you can check environments with no workloads yet as well as production environments, with no impact. Conversely, transient failures and packet loss are out of scope.

Explain

The blocking component and why

If the destination is not reachable, it returns the blocking component or combination of components along with an explanation code. If it is reachable, it lists the components along the path in order.

Verify

Validate before and after changes

Because analyses can be run through the API, use them as a step in your deployment pipeline to confirm that intended paths were opened or closed.

How analysis works

Define a path, get a verdict from the configuration model

A path consists of a source, a destination, a protocol, and a destination port. When you run an analysis, the result contains reachability, the forward and return path components, and the blocking reason. Below is a trimmed example result.

  1. Shows the shortest path reachable

    If there are several reachable paths, the shortest one is shown. To see other paths, run the analysis again including or excluding specific intermediate components.

  2. Blocking reasons as codes not reachable

    Codes such as CANNOT_ROUTE, ENI_SG_RULES_MISMATCH, and FIREWALL_RULES_RESTRICTION indicate the type of cause. Other components may also be blocking, so analyze again after each fix.

  3. Accounts for packet header rewrites

    When an intermediate component changes the header, as with IGW and NAT gateway address translation, it shows both the header leaving the source and the header arriving at the destination.

Features

Key features

Endpoints

Source and destination types

Specify EC2 instances, network interfaces, internet gateways, transit gateways and their attachments, virtual private gateways, VPC endpoints and endpoint services, and VPC peering connections. An IP address can also be a destination.

Evaluated

Components evaluated

Route tables, security groups, network ACLs, prefix lists, load balancers and target groups, NAT gateways, TGW route tables, VPN connections, and gateway endpoints are evaluated together along the path.

Network Firewall

Down to firewall rules

Evaluates both stateless and stateful 5-tuple rules in Network Firewall. When it encounters unsupported rules such as domain lists, Suricata rules, rule options, or tag-based resource groups, it adds a notice to the path details. The analysis fails if a rule group references a resource group.

Filters

Include or exclude intermediate components

Narrow the analysis so the path must traverse or avoid a load balancer, NAT gateway, Network Firewall, transit gateway, or peering connection, and verify the exact path you intend.

Cross-account

Organization-wide cross-account analysis

With Organizations trusted access enabled, the management account or a delegated administrator account can specify resources in other member accounts as sources and destinations.

Automation

Repeatable checks via API and CLI

Save paths with CreateNetworkInsightsPath and StartNetworkInsightsAnalysis, then re-analyze the same path after every change.

Analysis covers IPv4 only. It analyzes paths within a single Region, either inside one VPC or between VPCs connected by peering or a transit gateway. It does not consider TGW Connect attachments, TGW policy tables, target health, BYOIP advertisement status, or Traffic Mirroring. TCP paths through TGW route tables are analyzed in the forward direction only, and paths through a GWLB endpoint do not include the GWLB and its targets.

Reachability vs Network Access

Diagnose one path, or audit all access?

Both tools perform static analysis based on automated reasoning. Reachability Analyzer asks "can A reach B?", while Network Access Analyzer finds "paths that should not exist" as defined by a Network Access Scope.

Reference architecture

Path analysis across multiple accounts in an organization

From the delegated administrator account, specify an instance in account A as the source and an instance in account B as the destination. The analysis follows the path through the Transit Gateway routing in the network account and reports where it is blocked by a security group in account B. For VPC configuration see the VPC page, and for hub routing see the Transit Gateway page.

The management account can analyze resources in every account in the organization. A delegated administrator account can analyze member accounts other than the management account, plus management account resources explicitly shared with it. Complement it with VPC Flow Logs for actual traffic flows and Network Manager for global topology and route monitoring.

Getting started

Getting started

  1. STEP 1

    Define the path

    Specify the source and destination resources, the protocol (TCP or UDP), and the destination port. Optionally add source/destination address and port range filters.

  2. STEP 2

    Run the analysis

    Save the path and start an analysis. If the path must traverse or avoid specific intermediate components, specify them now.

  3. STEP 3

    Read the result

    If reachable, review the hop-by-hop path; if blocked, check the explanation code and the blocking component.

  4. STEP 4

    Fix and re-analyze

    After fixing routing or security groups, analyze the same path again. Any remaining blockers show up next.

  5. STEP 5

    Scale and automate

    For cross-account analysis, set up trusted access and a delegated administrator, and re-verify key paths through the API in your change pipeline.

Amazon VPC Flow Logs · IP traffic metadata · Observability

Record every flow through your VPC as a one-line record

VPC Flow Logs records IP traffic going to and from network interfaces as records keyed by the 5-tuple. Collection happens outside the traffic path, so throughput and latency aren't affected, and you can send records to CloudWatch Logs, Amazon S3, or Amazon Data Firehose for immediate analysis.

Why Flow Logs

The baseline log that answers "where was this packet blocked?"

Without packet capture, you can see who communicated, when, on which port, how much, and whether it was accepted or rejected. Network operations, security, and cost analysis all work from the same data.

Diagnose

Troubleshoot security groups and NACLs

Use REJECT records to find overly restrictive rules, and compare ingress and egress records of the same flow to spot return traffic missing from stateless NACLs.

Forensics

Security investigation and anomaly detection

Reconstruct peers around a suspected compromise, port scans, and unexpected outbound traffic from records. Amazon GuardDuty also analyzes VPC flow logs as a foundational data source.

Analyze

Traffic and cost analysis

Break down cross-AZ, internet, and peering traffic volume with the bytes, traffic-path, and az-id fields, and trace where data transfer costs come from.

Record format

Start with the default format; add the fields you need with a custom format

The default format uses the 14 version 2 fields in a fixed order. A custom format picks only the fields you want, in the order you want, and the record's version becomes the highest version among the chosen fields. The format can't be changed after creation; to change it, create a new flow log.

  1. v3 pkt-srcaddr · pkt-dstaddr

    When traffic passes through an intermediate layer such as a NAT gateway or EKS pods, these show the packet's original source and destination rather than the ENI address. vpc-id, subnet-id, instance-id, and tcp-flags are also v3.

  2. v4 · v5 Location and direction

    region, az-id, and sublocation (v4), plus flow-direction (ingress or egress), traffic-path (the egress path such as IGW, peering, VGW, or gateway endpoint), and pkt-src/dst-aws-service (v5) add context to the flow.

  3. v7 ecs-* fields

    ecs-cluster-name, ecs-service-name, ecs-task-arn, and others identify traffic per ECS task. They require permission to call the relevant ECS APIs, and non-ECS traffic shows '-'.

  4. v8+ Reject reasons and extended metadata

    reject-reason (v8) identifies flows rejected by VPC Block Public Access (BPA) or VPC Encryption Controls (EC). resource-id (v9) adds regional NAT gateways, encryption-status (v10) shows whether traffic is encrypted in transit, and v11 adds instance, ENI, and ASG tags, interface-type, and next-hop-* fields.

Traffic that isn't logged

Flow Logs doesn't capture all IP traffic. The traffic below produces no records, so if you need a record of DNS queries, also use Route 53 Resolver query logging.

Features

Main features

Scope

Choose capture scope

Create a flow log on a VPC or subnet and every ENI in it is covered, including ENIs created later. You can also watch a single ENI, or create flow logs per transit gateway, attachment, or regional NAT gateway.

Traffic type

ACCEPT · REJECT · ALL

Log only accepted traffic, only rejected traffic, or everything. For security group troubleshooting, collect only REJECT to cut log volume and cost.

Aggregation

1- or 10-minute aggregation

Groups the same flow into one record over the maximum aggregation interval. The default is 10 minutes; choosing 1 minute is more granular but produces more records. Nitro instance ENIs use 1 minute or less regardless of the setting.

Query

Logs Insights · Athena

In CloudWatch Logs, aggregate directly with Logs Insights queries; in S3, run SQL with Amazon Athena. The console can also generate a CloudFormation template for Athena integration.

Transit Gateway

TGW flow logs

Record flows for an entire transit gateway or per attachment. Find routing problems with source and destination VPCs and accounts, plus loss counters such as packets-lost-no-route and packets-lost-blackhole. Transit Gateway overview

Organization

Central collection · Organization-wide enablement

Send to S3 buckets or Firehose streams in other accounts using bucket policies or cross-account IAM roles. With CloudWatch telemetry enablement rules, flow logs to CloudWatch Logs are created automatically for existing and new VPCs in an organization, account, or tag scope.

Destinations

Comparing destinations

You can create several flow logs with different destinations and formats on the same resource. CloudWatch Logs suits immediate queries and alarms, S3 suits long-term retention and bulk analysis, and Firehose suits streaming to external tools.

Reference architecture

Three stages: capture, delivery, analysis

Flow Logs collects flow metadata from ENIs and transit gateways outside the traffic path, groups it into records every aggregation interval, and delivers them to destinations. Because each destination uses different analysis tools, it's common to create separate flow logs per purpose. To check statically whether the path itself is configured as intended, use Reachability Analyzer.

Getting started

Steps to turn on your first flow log

  1. STEP 1

    Scope and traffic type

    Choose a target among VPC, subnet, ENI, TGW, and regional NAT, and decide on ACCEPT, REJECT, or ALL. VPC overview

  2. STEP 2

    Prepare the destination

    Prepare a log group and IAM role, or an S3 bucket policy or Firehose stream.

  3. STEP 3

    Format and aggregation interval

    Choose default or custom format, a 1- or 10-minute interval, and for S3, Parquet and Hive partitions.

  4. STEP 4

    Create the flow log

    Create it in the console or with aws ec2 create-flow-logs and add tags.

  5. STEP 5

    Verify with queries

    Once records accumulate after a few minutes, check the top REJECT flows first with Logs Insights or Athena.

Pricing

Cost components

Flow Logs has no separate hourly charge; the log data it generates is billed at CloudWatch vended logs rates. Rates differ by destination and are tiered, decreasing as usage grows.

Log volume scales with the number of flows, the aggregation interval, and the number of fields chosen more than with traffic volume. Logging only REJECT or choosing only the fields you need reduces cost. Add cost allocation tags to destination resources (log groups, buckets, Firehose streams) to split flow log charges by team. See Vended Logs on the Amazon CloudWatch pricing page for current rates.

Why Network Firewall

보안 그룹과 NACL 다음 단계의 검사가 필요할 때

보안 그룹과 네트워크 ACL은 IP와 포트로 허용 여부를 정합니다. 도메인 기반 아웃바운드 통제, 프로토콜 탐지, 시그니처 기반 침입 방지가 필요하면 방화벽 계층을 더합니다.

Managed

운영 부담 없는 확장

트래픽에 따라 자동으로 확장되며, 가용성과 복원력은 AWS가 관리합니다. 어플라이언스 인스턴스를 직접 운영하지 않습니다.

Inspect

흐름 단위 심층 검사

포트와 무관하게 HTTPS 같은 프로토콜을 식별하고, 패킷 페이로드까지 규칙으로 검사합니다.

Central

하나의 정책, 여러 VPC

방화벽 정책 하나로 여러 VPC의 엔드포인트나 Transit Gateway 연결을 함께 관리합니다.

Stateful rules

규칙은 Suricata 문법 그대로 씁니다

아래는 아웃바운드 허용 목록 예시입니다. 새 방화벽 정책의 기본값인 strict order에서는 규칙 그룹은 우선순위 순서로, 그룹 안의 규칙은 적힌 순서대로 평가됩니다.

  1. Strict order 기본 · 권장

    새 정책의 기본 방식입니다. 규칙 그룹은 우선순위 번호가 낮은 것부터, 그룹 안의 규칙은 정의한 순서대로 평가합니다. 일치하는 규칙이 없을 때의 기본 액션을 정책에서 고르며, 새 정책은 Application drop established (server-directed only)가 기본입니다.

  2. Action order 레거시

    기존 정책 호환용 방식입니다. 모든 pass 규칙을 먼저 평가하고, 이어서 drop, reject, alert 순서로 평가합니다. 같은 액션 안에서는 priority 키워드로 순서를 정합니다. 규칙 그룹의 평가 순서는 정책과 같아야 합니다.

  3. reject는 TCP 전용

    일치한 트래픽을 차단하고 송신자에게 TCP RST를 보냅니다. FTP와 IMAP 프로토콜에는 쓸 수 없습니다.

Features

주요 기능

Stateless

Stateless 규칙

패킷 하나를 흐름 문맥 없이 출발지 · 목적지, 포트, 프로토콜로 판정합니다. pass, drop, stateful 엔진으로 forward 중 하나를 고릅니다.

Domain filtering

도메인 목록 규칙

HTTPS는 TLS SNI, HTTP는 Host 헤더로 도메인을 판단합니다. 허용 · 거부 목록에 더해 reject, alert 액션도 쓸 수 있고, .example.com처럼 하위 도메인 전체를 지정합니다.

TLS inspection

TLS 검사

ACM 인증서로 암호화된 트래픽을 복호화해 stateful 엔진에 넘기고 다시 암호화합니다. 인바운드는 서버 인증서를, 아웃바운드는 가져온 CA 인증서를 씁니다. session holding을 켜면 SNI 규칙 평가 전까지 연결 수립 패킷을 목적지로 보내지 않습니다.

Managed rules

AWS 관리형 규칙 그룹

도메인 · IP, 위협 시그니처(StrictOrder · ActionOrder 버전) 관리형 규칙 그룹과 AWS Marketplace 파트너 규칙 그룹을 정책에 추가합니다. Amazon 위협 인텔리전스 기반 active threat defense는 콘솔에서 새 정책을 만들 때 기본으로 켜지며, 별도 요금이 붙습니다.

Multi-VPC

여러 VPC 엔드포인트

VPC endpoint association으로 한 방화벽의 엔드포인트를 다른 VPC에도 둡니다. AWS RAM으로 방화벽을 공유하면 다른 계정 VPC도 같은 정책으로 보호합니다. 모든 엔드포인트가 AZ당 처리량을 나눠 씁니다.

Logging

Alert · Flow · TLS 로그

로그 유형별로 Amazon S3, CloudWatch Logs, Amazon Data Firehose 중 대상을 지정합니다. drop, alert, reject 규칙이 일치하면 alert 로그에 남습니다.

Web categories

URL · 도메인 카테고리 필터링

GenAI, 소셜 미디어, 스트리밍 같은 미리 정의된 웹 카테고리로 규칙을 씁니다. TLS 검사와 함께 쓰면 URL 단위로 더 세밀하게 통제합니다.

Containers

컨테이너 속성 기반 규칙

Amazon EKS의 namespace · cluster · label, Amazon ECS의 cluster · 속성으로 규칙 대상을 지정합니다. 와일드카드도 지원하며 추가 요금은 없습니다.

Preview

명시적 forward proxy

같은 방화벽 정책으로 explicit proxy 모드를 함께 쓰는 기능이 퍼블릭 프리뷰 중입니다(2026년 8월, US East (Ohio)). 정식 출시 전이므로 운영 설계에는 반영하지 마세요.

Deployment models

트래픽을 방화벽으로 보내는 네 가지 방법

방화벽은 라우팅으로 트래픽을 받습니다. 어느 라우팅 테이블에서 방화벽을 다음 홉으로 지정하느냐에 따라 배포 모델이 나뉩니다.

Reference architecture

Transit Gateway에 직접 붙이는 중앙 검사

스포크 VPC와 온프레미스 트래픽은 TGW 라우팅 테이블을 따라 방화벽 attachment로 갑니다. 방화벽이 쓰는 VPC는 Network Firewall이 관리하므로 보이지 않고, 검사를 통과한 트래픽은 목적지 VPC나 이그레스 VPC로 이어집니다.

Getting started

첫 방화벽을 배포하는 순서

  1. STEP 1

    규칙 그룹 작성

    stateless, stateful 규칙 그룹을 만들거나 관리형 규칙 그룹을 고릅니다.

  2. STEP 2

    방화벽 정책

    규칙 그룹을 묶고 평가 순서(기본값 strict order)와 기본 액션을 정합니다.

  3. STEP 3

    방화벽 생성

    VPC와 AZ별 방화벽 서브넷을 지정하거나, Transit Gateway(다른 계정 소유면 RAM으로 공유받은)에 직접 연결합니다.

  4. STEP 4

    라우팅 변경

    VPC 또는 TGW 라우팅 테이블에서 방화벽 엔드포인트나 attachment를 다음 홉으로 지정합니다.

  5. STEP 5

    로깅과 검증

    alert · flow 로그를 켜고, 허용과 차단이 의도대로 동작하는지 확인합니다.
